# Instruções do projeto

- Sempre que implementar algo (feature, fix, refactor), após codificar, atualize a documentação relevante (README.md, PRODUCT.md, etc.) se a mudança afetar o que está documentado.
- Sempre que implementar algo, após codificar, rode `fvm flutter analyze && fvm flutter test` para verificar se está tudo ok.
- Feature flags são controladas no Firestore (`config/recursos`, ver [lib/dados/config_admin.dart](lib/dados/config_admin.dart)) — interruptores booleanos, mais os convidados do chat em `convidados/{email}` — lidas por [lib/dados/recursos.dart](lib/dados/recursos.dart) (conversas, planos personalizados, voz, etc.). O painel `/admin` (só web e só o dono) edita sem reimplantar. Use esse mecanismo em vez de reimplementar gating na mão.
- O arquivo `.env.json` na raiz precisa existir localmente (chaves Firebase/Gemini) para rodar o app; não versionar o conteúdo dele.
- Versionamento (`version: X.Y.Z+N` em `pubspec.yaml`): o Android só atualiza por cima de um build com `+N` maior, sem precisar desinstalar, então todo bump soma 1 ao `+N`, que nunca volta atrás nem é zerado. Bug fix soma 1 ao patch e ao `+N` (`1.15.0+34` → `1.15.1+35`). Funcionalidade nova soma 1 à minor, zera o patch e soma 1 ao `+N` (`1.15.1+35` → `1.16.0+36`). Bumpe quando o push para `main` estiver prestes a acontecer. Refactor, ajuste de texto/documentação e iteração local não mexem na versão.
- Trabalhe sempre direto na branch `main`. Nunca crie branch nem worktree para implementar tarefas deste projeto — nada de isolamento por branch/worktree, mesmo quando um skill ou processo sugerir isso por padrão.
- Sempre que uma tela (`lib/telas/`) ou widget de UI (`lib/widgets/`) for criado ou alterado, após codificar, rode o agente `ui-reviewer` nos arquivos mudados e corrija os achados de gravidade alta antes de dar a tarefa por concluída.
